# Защита ЛР6

## Вступление

«Я построил сервисную цепочку для двух клиентов. Трафик к серверу проходит сначала через firewall, затем через шейпер. IP-адреса хостов не меняются. Путь выбирает OVS по правилам OpenFlow. VNFM управляет контейнерами и их подключением, а NFVO читает граф и отправляет правила в OpenDaylight. Я проверил работу цепочки, добавил второй firewall и восстановил связь после отказа первого».

## Показ в WSL

Откройте Ubuntu под `panindv`. Текущий стенд в состоянии после heal.

```bash
cd ~/nfv-lab4/lab6
whoami
export STUDENT=panin N=2
read -rsp 'Пароль ODL: ' ODL_PASSWORD
echo
export ODL_PASSWORD
```

1. `docker exec clab-panin-l6-sw ovs-vsctl show`. Покажите `is_connected: true` и OpenFlow-адрес контроллера. До установки потоков ping дал 0 из 2. Покажите рисунок 1 отчета.
2. `cat descriptors/shaper-vnfd.yaml`. Покажите тип функции, провайдера, две точки подключения, day-1 команду, лимит экземпляров. `docker exec clab-panin-l6-shaper1 tc qdisc show dev eth2` показывает TBF на 12 Мбит/с.
3. `docker exec clab-panin-l6-fw2 nft list ruleset`. Найдите правило TCP 8002 и счетчик. Скажите, что HTTP на 80 проходит, а запрос к слушающему 8002 получил 000 и увеличил счетчик drop.
4. `docker exec clab-panin-l6-sw ovs-ofctl -O OpenFlow13 dump-flows br0`. Укажите на приоритет 300. После heal первые три перехода c1 идут 1 → 5, 6 → 7, 8 → 9. В обратном направлении 9 → 8, 7 → 6, 5 → 1.
5. `cat vnffg.yaml`. Сейчас обе цепочки используют fw2. Скриншот scale-out показывает промежуточный вариант, где только c2 была переведена на fw2. При запросе client2 счетчик HTTP fw1 остался 6, fw2 вырос с 0 до 6. После остановки fw1 c1 потеряла связь, c2 сохранила ее. После переприменения графа первый ping c1 прошел через 6,36 с от команды остановки. Покажите рисунки 5 и 6.
6. `bash scripts/final-check.sh`. Видны VNF, ID и счетчики потоков, HTTP 200 у обоих клиентов и измерение вперед. Сравнение за 5 с у получателя показало 11,1 Мбит/с вперед и 471 Мбит/с назад. Шейпер установлен на выходе eth2 по направлению к серверу.

## Вопросы

- **Почему одной подсети недостаточно для ping?** Прежде чем отправить ICMP, клиент узнает MAC через ARP. OVS в secure без подходящих правил не пересылает кадры между этими портами. Нужен путь для ARP и IPv4.
- **Какие элементы VNFD соответствуют SOL001?** Образ и ресурсы описывают VDU. Два интерфейса соответствуют внешним точкам подключения. Ограничение числа экземпляров напоминает scaling aspect, список операций задает жизненный цикл. Для полного дескриптора нужны формальные типы TOSCA, связи, уровни масштабирования и примитивы управления.
- **Почему на переход нужны два правила?** ARP и IPv4 различаются по EtherType и полям адреса. В ответном трафике определяем цепочку по IP клиента как получателя.
- **Как получается 24 потока?** На цепочку шесть переключений OVS, по три на направление. Для каждого IPv4 и ARP. Две цепочки дают 2 × 6 × 2.
- **Почему stateful firewall требует симметрии?** Один экземпляр хранит состояние соединения. Если обратный пакет идет через другой экземпляр без общего состояния, он может быть признан новым или недопустимым. Балансировка должна сохранять привязку обоих направлений к одному экземпляру.
- **Чем scale-out отличается от heal?** Scale-out добавляет новый экземпляр и распределяет нагрузку. Heal восстанавливает сервис, переводя пострадавшую цепочку на рабочий экземпляр.
- **Что нужно автоматизировать для heal?** Контроль доступности VNF и портов, выбор резерва, обновление графа, подтверждение связи и уборку отказавшего экземпляра.
- **Где расходуется CPU?** OVS userspace и каждый veth/bridge добавляют обработку кадров и обход сетевого стека. Один замер скорости и снимок CPU не определяют точное узкое место.
- **Как ускорить NFVI?** OVS-DPDK обрабатывает пакеты в userspace с polling и требует выделенных ядер и hugepages. SR-IOV дает прямой доступ к VF, но ограничивает часть функций виртуального коммутатора. vhost-user ускоряет обмен с ВМ. SmartNIC переносит поддерживаемую обработку на сетевую карту.
- **Почему выбран netdev?** Текущее ядро WSL не поддерживает таблицы nftables bridge. В варианте netdev проверка выполняется на входах прозрачного Linux-моста. Это по-прежнему nftables и тот же результат для тестового трафика TCP 8002.
