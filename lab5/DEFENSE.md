# Защита ЛР5

## Вступление

«Я развернул небольшую сеть предприятия. В ЦОД стоит SONiC с FRR, а на границе и в филиале работают MikroTik CHR. HQ выполняет функции vCPE: получает сеть ЦОД по eBGP, дает серверу выход к провайдеру через NAT и проверяет трафик firewall. Сеть филиала подключена через WireGuard. Покажу маршруты, связь и управление через REST».

## Показ из WSL

```bash
cd ~/nfv-lab4/lab5
read -rsp 'RouterOS password: ' ROS_PASS; echo
export ROS_PASS
```

Команды выполняются под panindv. Ввод пароля скрыт.

1. `bash scripts/defense-check.sh topology`. «Это шесть узлов. На CHR заданы имена hq-panin и br-panin. Оба используют бесплатную лицензию».
2. `bash scripts/defense-check.sh bgp`. «У RouterOS сессия Established. FRR видит AS 65102 и два префикса. Оба маршрута идут через 10.2.1.2: выход по умолчанию и сеть филиала».
3. `bash scripts/defense-check.sh wan`. «Сервер получает HTTP 200. ISP пишет в журнале 100.64.1.2, значит NAT подменил исходный адрес. Пинг в обратном направлении начинается извне и получает 0 ответов. Два пакета попали в forward-default-deny». Скрипт добавляет тестовый маршрут на ISP только на время проверки.
4. `bash scripts/defense-check.sh wireguard`. «Филиал пингует сервер ЦОД. На провайдерском канале виден внешний UDP 13002 между WAN-адресами. Внутренний ICMP находится внутри зашифрованного туннеля. У пира есть handshake и ненулевые счетчики».
5. `bash scripts/defense-check.sh rest`. «GET читает имя, адреса и BGP. PUT создает временную запись, PATCH меняет её комментарий, DELETE удаляет запись и возвращает 204». Этот шаг меняет только временный объект в отдельном списке.
6. `bash scripts/defense-check.sh final`. «В конце вместе видны BGP, состояние туннеля, успешный ping филиала и HTTP 200 из ЦОД».

При короткой защите покажите шаги 1, 2 и 6 в терминале. Для NAT, firewall, захвата и REST используйте снимки по ссылкам в README.

## Вопросы преподавателя

- **Зачем CHR аппаратная виртуализация?** CHR здесь запускается внутри QEMU через KVM. Образ SONiC VS работает прямо как контейнер. Бесплатный CHR ограничивает исходящую скорость интерфейса до 1 Мбит/с, поэтому задержки и скорость стенда не характеризуют производительность реального оборудования.
- **Зачем убрать default через eth0 dc1?** Маршрут управления мог конкурировать с BGP default и уводить пакеты в Docker management. В стенде выбран eBGP-маршрут через Ethernet4 с расстоянием 20.
- **Что даёт if-installed?** HQ анонсирует default только при наличии маршрута по умолчанию в таблице. Это не проверка доступности каждого интернет-ресурса.
- **Почему ответ из Интернета пропускается?** Connection tracking относит ответ к established-соединению, начатому из ЦОД. Обратное преобразование NAT возвращает пакет к srv1.
- **Какие адреса видит ISP в WireGuard?** 100.64.1.2 и 100.64.2.2. На WAN виден UDP 13002. Адреса хостов ЦОД и филиала находятся в зашифрованной части.
- **Зачем allowed-address и отдельный маршрут?** Маршрут направляет пакет в WireGuard-интерфейс. Allowed-address сопоставляет назначения с пиром при отправке и проверяет адрес источника при приёме.
- **Как сеть филиала появилась в FRR?** HQ имеет статический маршрут к 10.2.200.0/24 через wg-br и включает этот префикс в BGP-анонс через output.network.
- **Почему приватный ключ не экспортирован?** Обычный RouterOS export скрывает чувствительные значения. При развёртывании маршрутизаторы сами создают приватные ключи, а в конфигурации пиров нужны публичные. Если требуется перенос ключей, применяют отдельное защищенное хранилище.
